# TC060 · Gói firmware sai chữ ký

- **Nhóm:** UC14 · **Loại:** Unhappy · **Ưu tiên:** P1
- **Kết quả:** `dat` — 2/2 dấu hiệu: từ chối, chữ ký · 24s
- **Thời gian:** 23.9 s · **0 lời gọi công cụ**, 0 lời gọi HỎNG

## Người gõ

> Nếu gói firmware gửi lên bị sửa đổi, chữ ký không khớp thì sao?

## Đề bài chờ

> Bootloader từ chối, ghi log

## Tác tử đã đi những nước nào

_Không gọi công cụ nào._

## Nguyên văn lời đáp

```
[Tác tử] ## Tóm tắt: Bản cập nhật bị loại bỏ ngay lập tức, Slot A tiếp tục chạy bình thường

> Nếu gói firmware bị sửa đổi trên đường truyền (do lỗi đường truyền hoặc bị kẻ gian can thiệp chèn mã độc), **phép kiểm tra chữ ký số (Cryptographic Signature Verification) sẽ thất bại**. Hệ thống sẽ **từ chối kích hoạt Slot B, đánh dấu bản ghi là không hợp lệ (INVALID), và tiếp tục chạy an toàn trên Slot A**. Thiết bị không bao giờ khởi động vào bản firmware bị can thiệp.

---

## 1. Cấu trúc gói tin cập nhật có chữ ký số

Để kiểm tra được tính toàn vẹn và nguồn gốc, gói firmware OTA thường được đóng gói theo định dạng chuẩn (như MCUboot hoặc chuẩn riêng):

```
+-------------------------------------------------------------------------+
|                              GÓI FIRMWARE OTA                           |
| +---------------------------------------------------------------------+ |
| | Header: Kích thước, Phiên bản (Version), Mã băm (SHA-256 Hash)      | |
| +---------------------------------------------------------------------+ |
| | Payload: Mã nhị phân firmware thực tế (.bin)                        | |
| +---------------------------------------------------------------------+ |
| | Signature: Chữ ký số tạo bởi Private Key của nhà phát triển         | |
| |            (thường dùng ECDSA P-256 hoặc Ed25519 / RSA-PSS)         | |
+-------------------------------------------------------------------------+
```

Trong đó:
- **Khóa bí mật (Private Key)**: Chỉ bạn giữ trên máy chủ build/phát hành firmware an toàn, dùng để ký gói tin trước khi gửi đi.
- **Khóa công khai (Public Key)**: Được nhúng cố định (hardcoded) vào trong mã nguồn của **Bootloader** hoặc lưu trong vùng nhớ chỉ ghi một lần (**OTP / eFuse**) của chip.

## 2. Quy trình xử lý cụ thể khi chữ ký không khớp

```
[ Nhận xong gói OTA vào Slot B ]
              │
              ▼
[ Tính toán mã băm SHA-256 của toàn bộ Slot B ]
              │
              ▼
[ Dùng Public Key giải mã & đối soát Signature ]
              │
      ┌───────┴───────┐
    Khớp            KHÔNG KHỚP (Phát hiện can thiệp/lỗi)
      │               │
  (Hợp lệ)            ▼
             1. Tuyệt đối KHÔNG ghi cờ chuyển boot sang Slot B.
             2. Ghi đè hoặc xóa Sector đầu (Header) của Slot B.
             3. Đánh dấu trạng thái Slot B = INVALID / CORRUPTED.
             4. Gửi mã lỗi (Error Telemetry) về máy chủ:
                OTA_ERR_VERIFY_SIGNATURE_FAILED.
             5. Tiếp tục thực thi bình thường trên Slot A.
```

### Chi tiết các bước bảo vệ:

1. **Khóa quyền khởi động (Boot lock)**:
   - Bootloader chỉ chuyển cờ `PENDING_BOOT` trong Metadata khi và chỉ khi hàm `crypto_verify_signature()` trả về mã thành công `0` (`SUCCESS`).
   - Một bit bị thay đổi trong payload sẽ làm mã băm SHA-256 thay đổi hoàn toàn (hiệu ứng tuyết lở - avalanche effect), dẫn tới việc xác thực chữ ký sai lệch toán học 100%.

2. **Vô hiệu hoá phân vùng Slot B**:
   - Sau khi phát hiện chữ ký sai, hệ thống sẽ xóa ngay sector chứa
```
